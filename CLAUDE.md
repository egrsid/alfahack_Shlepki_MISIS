# Проект: хакатон Альфа-Банк × Changellenge — «AI-агент для разработки ML-моделей» (трек AutoML)

## Суть
Нужно написать универсального AI-агента (LLM-управляемого), который получает текстовое описание ML-задачи и CSV-файлы
(`train.csv`, `test.csv`, `data_dictionary.csv`, `sample_submission.csv`) и сам: анализирует данные, определяет тип задачи,
пишет и запускает код, обучает модель, валидирует, формирует файл предсказаний.
Сдаётся КОД агента (ZIP с `solution.py` в корне), а не модель. Платформа запускает его на разных задачах.

## Оценка
- Public: 2 известные задачи.
  1. Регрессия — годовое удельное энергопотребление зданий (`site_eui`), метрика RMSE. train 53 308 × 64, test 22 449 × 63.
  2. Мультикласс — тип кибератаки (`attack_cat`), основная метрика Macro F1. train 87 670 × 44, test 41 166 × 43.
- Private: 2 скрытые новые задачи (метрики и содержание не раскрыты). Берётся сабмит с лучшим public score, код не меняется.
- Баллы нормируются относительно бейзлайна (хуже или равно бейзлайну → 0):

$$S_{reg} = 100 \cdot \max\left(0,\; 1 - \frac{RMSE}{B_{RMSE}}\right), \qquad
S_{cls} = 100 \cdot \max\left(0,\; \frac{MacroF1 - B_{F1}}{1 - B_{F1}}\right)$$

$$Score = \frac{S_1 + S_2}{2}$$

Главное: надёжность и универсальность на НЕЗНАКОМЫХ задачах, а не подгонка под public.

## Подключение к LLM
- Модель: `qwen/qwen3.8-27b`. Протокол: OpenAI-совместимый (`{OPENAI_BASE_URL}/chat/completions`).
- Base URL (разработка): `https://changellenge.up.railway.app/v1`.
  Запасной для российских хостингов: `https://api.alfahack-gateway26.ru/v1`.
- API-ключ (`sk-...`) выдан команде. **Никогда не писать ключ в код, в `CLAUDE.md`, в коммиты, чаты и логи.**
  Локально хранить в `.env` (добавлен в `.gitignore`) или в переменных окружения.
- Лимит: 600 ₽ в день на ключ, бюджет общий на всю команду. При ошибке `Budget has been exceeded` ждать сброса в 3:00 МСК.
  Поэтому: тестовые вызовы короткие, логировать расход токенов, кэшировать ответы, не гонять LLM-цикл без нужды.
- **На платформе** адрес и ключ подставляются переменными окружения `OPENAI_BASE_URL`, `OPENAI_API_KEY` (и опционально `OPENAI_MODEL`).
  Свои адрес и ключ в коде прописывать нельзя. Имя модели можно взять из `OPENAI_MODEL` или передать любое — прокси подставит модель задачи.
- Клиенты `openai` и `langchain-openai` читают переменные сами: достаточно `OpenAI()` без `api_key` и `base_url`.
- После старта скрипта доступен только предоставленный прокси: свой хост, прямой адрес модели и `pip install` из кода не работают.
- Использовать библиотеку для запросов только из списка зависимостей платформы (проверить, что `openai`/`httpx`/`requests` есть в `requirements.txt`).

Локальная настройка:

```sh
# Linux / macOS
export OPENAI_API_KEY="sk-..."          # подставить свой, не коммитить
export OPENAI_BASE_URL="https://changellenge.up.railway.app/v1"
```

Минимальный вызов:

```py

print(response.choices[0].message.content)
```

## Формат сдачи и запуск
- ZIP до 100 МБ, **все файлы строго в корне архива, без папок**: `solution.py` (точка входа), `requirements.txt`, дополнительные корневые `.py`-модули.
  Копируются только корневые `.py` и `requirements.txt`. Модуль в подпапке при запуске будет недоступен → риск 0 баллов.
  Значит, структура проекта плоская: все модули агента лежат рядом с `solution.py`.
- Сторонние пакеты и `.whl` добавлять нельзя. Зависимости ставит платформа из корневого `requirements.txt`.
- Команда запуска на платформе: `python3 solution.py task.md`. Скрипт работает в одной папке с `task.md`
  (текстовое описание задачи). Итоговый `submission.csv` сохранять **туда же, рядом с `task.md`**.
- Промежуточные файлы можно создавать в каталоге задачи, в его подкаталогах и в `/tmp`.
- Интерфейс (переменные окружения, расположение данных, формат вывода) также зафиксирован в `tools/baseline.py` — сверяться с ним.
- Проверка идёт в системе Boosters: статус «Решение находится на проверке» значит только «в очереди». После проверки — «Точность вычисления: …» или ошибка.
- Частые ошибки: «Превышено время обработки» (3 часа, включая запросы к LLM); «Не хватает данных в решении: отсутствует файл …»
  (нет `submission.csv` рядом с `task.md`); «Ошибка формата данных» (формат сабмита не как в `sample_submission.csv`).
  При обращении к организаторам прикладывать текст ошибки или скриншот и время отправки.

## Блоки работ
0. Организационный: baseline, requirements.txt, данные, LLM-ключ, окружение Python 3.12.
1. Разбор интерфейса `baseline.py` и `task.md`.
2. Понимание задачи: тип задачи, target, id-колонка, метрика, формат сабмита (из `task.md`, `data_dictionary.csv`, `sample_submission.csv`).
3. Детерминированный fallback без LLM: авто-предобработка + быстрый бустинг с CV; `submission.csv` пишется на диск СРАЗУ.
4. Агентный цикл AutoResearch: гипотеза → эксперимент (код в subprocess с таймаутом) → оценка по CV → следующая итерация; память экспериментов.
5. Защита: валидация без утечек, перехват ошибок сгенерированного кода, ретраи, защита от «обмана метрики».
6. Бюджеты: время (3 ч) и токены между исследованием и финальным обучением; стоп-критерии; финальный ансамбль или переобучение на всём train.
7. Универсальность: тесты на других табличных датасетах (регрессия, бинарная/мультикласс, дисбаланс, пропуски, категории, строки).
8. Упаковка плоского ZIP, проверка запуска локально (`python3 solution.py task.md`, при желании в Docker без сети), экономия сабмитов.

## Текущая цель: подключить LLM и получить первую работающую версию
Порядок (не перескакивать вперёд):
1. Окружение: Python 3.12, зависимости строго из `requirements.txt`; прочитать `baseline.py` (ответ организаторов про mcp: пакет не установлен в контейнере. сам скрипт сабмита предоставляет модели инструменты: модель выбирает действие, а скрипт выполняет его)
2. Smoke-test LLM: один короткий запрос через `OpenAI()` с переменными окружения; убедиться, что ответ приходит. Если основной URL недоступен — запасной.
3. Fallback-пайплайн без LLM: читает `task.md` и CSV, определяет target/тип задачи по `sample_submission.csv`, обучает быстрый бустинг,
   пишет `submission.csv` рядом с `task.md`. Это страховка от падения LLM и от лимита времени.
4. Минимальная LLM-интеграция: LLM читает `task.md` и `data_dictionary.csv` и возвращает JSON
   (тип задачи, target, id-колонка, метрика, замечания по признакам). Ответ валидировать; при любой ошибке — откат на эвристики из п. 3.
5. Прогнать целиком локально на обеих public-задачах, сверить формат `submission.csv` с `sample_submission.csv`.
6. Собрать плоский ZIP, сделать первый сабмит как точку отсчёта, записать score.

Рабочие правила для кода:
- `submission.csv` пишется как можно раньше и перезаписывается только когда есть улучшение по CV.
- Любой вызов LLM: таймаут, ограниченное число ретраев, логирование токенов, аккуратная обработка `Budget has been exceeded`; при отказе LLM решение всё равно должно завершиться и оставить `submission.csv`.
- Общий дедлайн по времени с запасом до 3 часов (рекомендация: остановка экспериментов заранее, чтобы успеть финальное обучение и запись файла).
- Код, сгенерированный LLM, исполняется в отдельном процессе с таймаутом; не доверять его выводу без проверки.
- Ничего не скачивать из интернета и не вызывать `pip` из кода.

## План работы команды (5 человек)

Этот раздел — общий план, живёт в `main`. В каждой feature-ветке лежит свой подробный план `docs/plans/<имя-ветки>.md`
(`docs/` не попадает в ZIP, упаковываются только корневые `.py` и `requirements.txt`).

### Принципы декомпозиции
- Агент = набор плоских модулей в корне рядом с `solution.py`. Каждый модуль принадлежит одному человеку → минимум merge-конфликтов.
- Модули общаются только через контракты из `schemas.py` (см. ниже). Контракты замораживаются на Этапе 0; менять их — только через PR с согласием всех.
- Главный риск — не качество, а падение на незнакомой задаче. Поэтому: fallback без LLM независим от агента, агент не может испортить `submission.csv` (пишет только при улучшении CV), любое исключение перехватывается в `solution.py`.
- В `baseline.py` используется `mcp`, но в контейнере его нет (ответ организаторов). Свой цикл «модель выбирает действие → скрипт выполняет» пишем на чистом `openai` + `subprocess`. Не полагаться на нативный tool-calling Qwen как единственный путь: нужен также текстовый протокол (JSON / блок ```python), который парсим сами.
- Метрику эксперимента считает ХАРНЕСС (наш код), а не код, сгенерированный LLM, — защита от «обмана метрики». LLM-код возвращает только признаки / параметры / предсказания, CV-сплиты и подсчёт метрики фиксированы.

**P1 — тимлид, интеграция, харнесс оценки, тюнинг, ансамбль**
- `evaluator.py` — ключевой модуль честной оценки (на нём стоит и агент P4, и fallback P3): фиксированные CV-сплиты (stratified/group/time по `TaskSpec`, один сид на весь запуск), функция `evaluate(spec, build_features, model_params, ...) -> Candidate` с OOF и test-предсказаниями, шум CV (std по фолдам) для порога «улучшение реально», отложенная часть train, которую агент не видит (hold-out для финальной проверки на переобучение под CV). Метрику считает через `metrics.score`.
- `eda.py`: `profile(train, test, spec) -> dict` — компактный профиль данных для LLM (типы, пропуски, кардинальность, распределение таргета, дисбаланс классов, корреляции с таргетом, дрейф train/test, подозрение на утечку, дубликаты), не более ~2–3 тыс. токенов.
- `tuning.py`: подбор гиперпараметров LightGBM/CatBoost/XGBoost через `optuna` с лимитом по времени из `Deadline`; предустановленные «рецепты» под тип задачи, которые агент может вызывать одной строкой.
- `ensemble.py`: финальный блендинг/стекинг OOF-предсказаний лучших кандидатов (веса по CV, защита от переобучения), переобучение на всём train, выбор между «лучший одиночный» и «ансамбль» по hold-out.
- Этап 0: скелет репозитория, `schemas.py` с контрактами, `.env.example`, правила веток (см. ниже), защита `main`.
- `solution.py`: читает `task.md` → `understand_task` → запускает fallback → (если LLM жив и есть время) `agent.research` → финальный ансамбль → валидация `submission.csv`. Весь агентный блок в `try/except`, при любом сбое остаётся fallback-сабмит.
- `budget.py`: единый `Deadline` (старт процесса, жёсткий лимит 3 ч, мягкие рубежи: fallback ≤ T+15 мин, остановка исследований T+2ч05, финал ≤ T+2ч35, запас 25 мин), счётчик токенов/₽, режим `LLM_DISABLED=1`.
- Единственный, кто делает сабмиты на платформу (3 в день!): ведёт таблицу «версия/коммит → public score» в `docs/submissions.md`. Решает, какой коммит отправлять.
- Сборка плоского ZIP, проверка, что в корне архива только `.py` и `requirements.txt`, в `requirements.txt` нет лишнего, ключей нет.

**P2 — LLM и понимание задачи**
- `llm_client.py`: обёртка над `OpenAI()` (ключ/URL только из env), таймаут, ограниченные ретраи (`tenacity`), обработка `Budget has been exceeded` (не ретраить, поднять `LLMUnavailable`), учёт токенов, дисковый кэш ответов (`.llm_cache/`, в `.gitignore`), методы `chat()` и `chat_json(schema)` с валидацией (`jsonschema`/`pydantic`) и 1–2 попытками «починить» JSON. Smoke-тест на основе `check_llm.py`. Запасной base URL — только через env, не в коде.
- `task_understanding.py`: `understand_task(task_dir, llm|None) -> TaskSpec`. Сначала детерминированные эвристики (id-колонка и target из `sample_submission.csv`, тип по таргету, метрика по regex из `task.md`), затем LLM уточняет (метрика, тип, замечания по признакам из `data_dictionary.csv`, колонки-утечки, id-подобные, даты, текст). Ответ LLM валидируется и сверяется с реальными колонками; при расхождении — эвристики. Должен работать, когда нет `data_dictionary.csv` или формат колонок другой (сейчас у двух задач разные наборы колонок словаря).
- Поддержать нестандартное: бинарная классификация (нужны вероятности для AUC/logloss?), мультилейбл, несколько таргетов в `sample_submission.csv`, таргет-строки, метрики RMSE/MAE/RMSLE/MAPE/R²/F1(macro/micro/weighted)/accuracy/AUC/logloss.

**P3 — ML-ядро (страховка)**
- `fallback.py` + `preprocess.py`: перенос и развитие текущего `solution.py` (v0, LightGBM без CV). Авто-предобработка: пропуски, категории (в т.ч. высокая кардинальность), даты, строки, константные и id-подобные колонки, дубликаты; K-fold CV (stratified для классификации); LightGBM + CatBoost (+XGBoost по времени); для классификации — class_weight/пороги под Macro F1; для регрессии — опционально лог-таргет, выбирается по CV. Пишет `submission.csv` СРАЗУ после первой модели и перезаписывает только при улучшении CV. Должен укладываться в ~15 мин на 8 CPU и в память 32 ГБ.
- `metrics.py`: реестр метрик (имя → функция, направление, нужны ли вероятности), единый `score(metric, y_true, y_pred)`. Именно им считают CV и fallback, и агент.
- `submission.py`: сверка с `sample_submission.csv` (колонки, порядок, число строк, множество id, допустимые классы, NaN) и запись. Это единственная точка записи `submission.csv`.
- CV в `fallback.py` на первых порах свой простой; когда P1 смержит `evaluator.py`, переходит на него (единые сплиты у fallback и агента).
- Ориентир: на public-задачах fallback должен заметно бить `baseline.py` организаторов.

**P4 — AutoResearch-агент (владелец: @egrsid)**
- `agent.py`: цикл «гипотеза → код → запуск в песочнице → оценка харнессом → решение → следующая итерация». Один агент, роли реализуются разными промптами (аналитик данных → генератор гипотез → кодер → критик). Шаги: (1) EDA-сводка по данным (компактная, не гнать сырые данные в LLM), (2) список гипотез по приоритету (признаки, кодирование, выбросы, лог-таргет, гиперпараметры, выбор модели, отбор признаков), (3) для каждой — код фичей/параметров в фиксированном шаблоне (`def build_features(train, test, spec)` и/или `PARAMS = {...}`), (4) оценка тем же CV и тем же сидом, что у лучшего (сравнение справедливо), (5) принять, если улучшение больше шума CV (порог по std между фолдами).
- `memory.py`: журнал экспериментов (гипотеза, дифф, CV-оценка, время, ошибка) → в промпт попадает сжатая сводка; сохранять на диск (JSONL) для отладки.
- `prompts_agent.py`: промпты на русском/английском (выбрать по качеству Qwen), с примерами формата ответа.
- Бюджеты: макс. число итераций, макс. токенов на задачу, таймаут на эксперимент (из `Deadline`), остановка при 3 неудачах подряд / отказе LLM. Стоимость вызовов экономить: сводки вместо данных, короткие ответы, кэш.
- Стратегии (поздний этап): подбор гиперпараметров через `optuna` по времени, добавление найденных признаков в ансамбль, обработка ошибок модели (анализ худших объектов).

**P5 — песочница, защита, универсальность**
- `sandbox.py`: `run_code(code, cwd, timeout, memory_limit) -> ExecResult(stdout, stderr, returncode, artifacts)` — отдельный процесс, жёсткий таймаут с убийством дерева процессов, лимит выходных данных, чистый `env` (без ключей!), рабочий каталог — подкаталог задачи или `/tmp`. Передача результата через файл (parquet/JSON), а не через stdout.
- `guards.py`: проверки «не доверяй выводу»: код не читает `test`-таргет и не трогает `submission.csv`/CV-сплиты; нет утечки (target-кодирование только внутри фолда, id/индекс как признак); предсказания на test той же формы, без NaN/inf, диапазон разумен; сравнение распределений OOF и test-предсказаний; штраф/отклонение подозрительно «чудесного» улучшения.
- `tests/` и `tools/make_datasets.py`: набор синтетических и открытых табличных датасетов, которых нет в ZIP (sklearn: регрессия, бинарная, мультикласс, сильный дисбаланс, пропуски, высококардинальные категории, строки/даты, мало строк, много колонок, таргет-строка, другая метрика). Генерация папок в формате задачи (`task.md`, `train.csv`, `test.csv`, `data_dictionary.csv`, `sample_submission.csv`). Скрипт `tools/run_all.sh` прогоняет `solution.py` на всех и сверяет формат.
- `feature/docker-check`: прогон в Docker с Python 3.12, `--network none`, 8 CPU / 32 ГБ, только корневые файлы из ZIP; проверка, что нет импортов вне `requirements.txt` и нет подкаталогов-модулей.

### Контракты между модулями (`schemas.py`, замораживаются на Этапе 0)
```python
@dataclass
class TaskSpec:
    task_dir: Path
    id_col: str
    target: str | list[str]
    task_type: Literal["regression", "binary", "multiclass", "multilabel"]
    metric: str                 # ключ из metrics.py
    greater_is_better: bool
    feature_notes: dict[str, str]   # из data_dictionary / LLM
    drop_cols: list[str]            # id-подобные, утечки
    cat_cols: list[str]; date_cols: list[str]; text_cols: list[str]
    raw_task_text: str
    source: Literal["heuristic", "llm"]

@dataclass
class Candidate:
    name: str
    cv_score: float; cv_std: float
    oof: np.ndarray; test_pred: np.ndarray   # в «сырых» единицах (вероятности для классификации)
    meta: dict

# понимание:   understand_task(task_dir, llm: LLMClient | None) -> TaskSpec            (P2)
# LLM:         LLMClient.chat(messages, **kw) -> str ; .chat_json(messages, schema) -> dict   (P2)
# fallback:    fallback.run(spec, deadline) -> Candidate                                (P3)
# метрики:     metrics.score(name, y_true, y_pred) -> float ; metrics.get(name)         (P3)
# сабмит:      submission.write(spec, pred) -> Path  (валидирует и пишет)               (P3)
# песочница:   sandbox.run_code(code, cwd, timeout) -> ExecResult                       (P5)
# защита:      guards.check_candidate(spec, cand, baseline) -> list[str]  (пусто = ок)  (P5)
# агент:       agent.research(spec, best, llm, deadline) -> list[Candidate]             (P4)
# ансамбль:    ensemble.blend(spec, cands) -> Candidate                                 (P1)
# оценка:      evaluator.evaluate(spec, build_features, params, deadline) -> Candidate  (P1)
# профиль:     eda.profile(train, test, spec) -> dict                                   (P1)
# тюнинг:      tuning.tune(spec, model_name, deadline) -> dict (best params)            (P1)
# дедлайн:     Deadline(total=...).left() / .stage("research")                          (P1)
```

### Git-процесс
- `main` защищён: прямые коммиты запрещены, только PR. В `main` всегда лежит запускаемая версия (`python3 solution.py task.md` не падает).
- Ветка на фичу: `feature/<короткое-имя>` от свежего `main`; живёт 1–2 дня, не более. Мелкие PR лучше больших. Перед PR: `git fetch && git rebase origin/main`.
- Названия коммитов: `feat|fix|test|docs|refactor: что сделано` (по-русски или по-английски, единообразно). Не коммитить: `.env`, ключи, данные (`*.csv`), `*.zip`, `.venv`, `.llm_cache/`. Перед коммитом `git diff --cached | grep -i "sk-"` — пусто.
- PR: описание «что и зачем», как проверить (команда), результат на public-задачах (CV), тесты. Ревью — минимум один человек, не автор, чаще — владелец смежного модуля. Мерж — squash.
- Файл другого владельца правим только через PR к нему/с его согласия. `solution.py` и `schemas.py` — только P1.
- План ветки: первым коммитом в ветку добавить `docs/plans/<ветка>.md` (цель, входы/выходы, шаги, критерии готовности, риски). Можно просить Claude Code расширить его по этому разделу.
- Сообщение в чат команды при мердже в `main`: что изменилось и нужно ли всем сделать `git pull --rebase`.

### Этапы и порядок мержей
**Этап 0 — старт (все, ~1–2 ч).** P1: скелет + `schemas.py` + `budget.py`-заглушка → в `main`. Все: клонируют, создают `.venv` на Python 3.12 из `requirements.txt`, кладут свой `.env`, прогоняют `python3 solution.py task.md` на обеих public-задачах (папки `Регрессия/`, `Многоклассовая классификация/` лежат локально, в git не идут). P2: `tools/check_llm.py` — убедиться, что LLM отвечает.
**Этап 1 — параллельно (ветки независимы):** P2 `llm-client`, P3 `fallback-pipeline` + `metrics-submission`, P4 `agent-loop` на заглушках LLM/песочницы (мок-клиент), P5 `sandbox` + `test-datasets`, P1 `time-budget` + `evaluator-harness` + `eda-profile` + интеграционный каркас `solution.py` (P4 до мержа харнесса работает с интерфейсом `evaluator.evaluate` и заглушкой). Порядок мержа: `skeleton` → `evaluator-harness`, `metrics-submission`, `llm-client`, `sandbox` (они почти ни от кого не зависят) → `fallback-pipeline`, `task-understanding` → `agent-loop`.
**Этап 2 — первая работающая версия:** P1 собирает `solution.py` из мерженных модулей, прогон на public-задачах и на датасетах P5, **первый сабмит** (fallback + понимание задачи, без цикла) → записать score как точку отсчёта.
**Этап 3 — AutoResearch и качество:** `agent-loop` + `guards-validation` в `main`, `tuning`, `final-ensemble` (P1), `experiment-memory`, `agent-strategies` (P4). Контроль бюджета LLM (₽/день общий — договариваться, кто когда гоняет). Сабмит №2 с агентом, сравнение с первым.
**Этап 4 — универсальность и надёжность:** P5 гоняет весь набор датасетов + chaos-тесты (LLM недоступен, мусорный JSON, бесконечный цикл в LLM-коде, OOM, test без id, неизвестная метрика); все чинят найденное. `feature/docker-check`.
**Этап 5 — заморозка:** feature freeze за N часов до дедлайна (N согласовать), только багфиксы. P1 собирает ZIP, финальный прогон в Docker без сети, сабмит. Приватный результат определяется кодом лучшего public-сабмита → не оставлять последние сабмиты «на авось», держать запас сабмитов.

### Критерии готовности (Definition of Done) для любой ветки
- Модуль работает на обеих public-задачах и хотя бы на одном датасете P5 (другой тип задачи).
- Ни при каких входах не оставляет процесс «висеть» (таймауты) и не ломает `submission.csv`.
- Нет ключей, абсолютных путей к своей машине, пакетов вне `requirements.txt`, вызовов `pip` и сети кроме LLM-прокси.
- Короткая запись в `docs/plans/<ветка>.md`: что сделано, как проверить, известные ограничения.

### Риски и что на них смотреть
- Qwen возвращает невалидный JSON / ломает формат → строгая валидация, ретраи, откат на эвристики.
- Лимит ₽ общий на команду → кэш, моки в тестах, `LLM_DISABLED=1` по умолчанию в юнит-тестах.
- Разное «железо»: на платформе 8 CPU/32 ГБ, у нас — по-разному → все времена брать из `Deadline` и замерять, не хардкодить.
- Скрытые задачи могут быть другого типа (бинарная с AUC, MAE, текст в колонках) → не подгонять под две public-задачи, смотреть на набор P5.
- Утечки и переобучение на CV из-за множества гипотез → фиксированные сплиты, порог улучшения > шума, финальная проверка на отложенной части, которую агент не видит.

## Структура репозитория (сводка; подробно — `README.md`)
- **Корень = ровно содержимое ZIP**: `solution.py`, `requirements.txt` и плоские модули решения. Вспомогательное в корень
  не класть (платформа копирует все корневые `.py`): организаторский `baseline.py` и `check_llm.py` — в `tools/`.
- `tools/` — вне ZIP: `make_zip.py` (сборка из корня по списку `FILES` + проверки `package.py`, `--smoke`),
  `package.py` (P3: сборка из распакованного архива с подменой модулей), `make_datasets.py` + `run_all.py`
  (12 тестовых задач и прогон ZIP на них), `try_agent.py` (короткий прогон агента), `baseline.py`, `check_llm.py`.
- `tests/` — pytest всех модулей, без LLM (`LLM_DISABLED=1`, MockLLM). `docs/plans/<ветка>.md` — план и итоги каждой ветки,
  `docs/plans/integration-submission.md` — как собрано решение и замеры, `docs/submissions.md` — таблица сабмитов.
- Конвейер `solution.py`: понимание задачи (`task_understanding`) → `fallback` (P3) → AutoGluon (`automl`, до 40 мин, на
  тех же фолдах) → агент (`agent`, стартует с лучшего кандидата fallback и добавляет признаки) → бленды (`ensemble`) →
  запись только при честном выигрыше над уже записанным и после `guards` → проверка файла.
